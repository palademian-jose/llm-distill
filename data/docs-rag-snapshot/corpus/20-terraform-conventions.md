# Terraform Conventions

Owner: Platform

## Scope

All cloud infrastructure is managed with Terraform. Creating resources in the
cloud console is not allowed in production; `drift-detector` runs nightly and
opens a ticket for any resource that differs from state.

## Repository layout

Infrastructure lives in the `infra-live` repository, organised by account,
region and environment:

```
infra-live/
  modules/                 # reusable modules, versioned with git tags
  accounts/<account>/<region>/<env>/<stack>/
```

A stack is a single Terraform root module with its own state. Stacks are
kept small: a stack that takes longer than five minutes to plan is split.

## Versions

Terraform 1.9 is pinned in `.terraform-version` and installed by `mise`.
Provider versions are pinned with `~>` to the minor version and updated by
Renovate monthly.

## State

State is stored in an object storage bucket with versioning enabled and a
DynamoDB-style lock table. State files are never edited by hand; use
`terraform state mv` or `import` blocks. Secrets never go into state: resources
that need secrets read them from Vault at apply time through the Vault
provider.

## Workflow

1. Open a pull request. CI runs `terraform fmt -check`, `tflint`, `checkov`
   and `terraform plan`, and posts the plan as a comment.
2. A Platform code owner reviews the plan output, not just the code.
3. On merge, `atlantis` applies the plan. Applies that touch production
   require a second approval.

Manual `terraform apply` from a laptop is blocked for production accounts by
the credential policy.

## Module standards

Modules expose variables with descriptions and types, outputs for every
resource identifier a consumer might need, and a `README.md` generated by
`terraform-docs`. Modules are versioned with semantic version tags and
consumed by tag, never by branch.

## Tagging

Every resource carries the tags `team`, `service`, `environment` and
`cost-centre`. The cost allocation report groups spend by these tags; untagged
resources show up in a weekly "unallocated spend" report sent to Platform.

## Destroying resources

`terraform destroy` is never run against production. Resources are removed by
deleting them from code and reviewing the plan, which must show the expected
destroy count in the pull request description.
